What you hand over

One question, one package, in a public repository

  • Start from labs/capstone/starter and your choice from Lab 3.4.
  • Route first: fill data_handling.md before the first request.
  • Log as you go: every assisted step, with its transcript.
  • Recompute each headline number without the assistant, and write its note.
  • Five runs of one request, compared.
  • README: numbers written from headline.json, and the disclosure paragraph.

Never in the repository

A key, or a row or example value of a Restricted table, in any file or transcript.

Before you hand it over

Run capstone/package.py check. It lists what the package still lacks.

The two-hour plan, minute by minute, is in labs/capstone/README.md. The usual failure is spending ninety minutes on the analysis and leaving thirty for everything that is scored: say so now. A participant with no working key writes the code themselves, logs it as written by the analyst and says so in the disclosure; the package is scored the same way.

How packages are scored

The rubric

30%

25%
Data handling and disclosure
15%
Findings
15%
Findings are 15 of 100. A smaller question with every headline number recomputed scores above a larger one that nobody checked.

Walk through each criterion with what full marks look like; the table is in labs/capstone/README.md. Verification: every headline number recomputed another way, with joins, filters and denominators checked. Reproducibility: the peer reaches every headline number from the log. A verified null result earns full marks for findings.

Build the package

Two hours

Commit as you go: the history is part of the evidence. Stop analysing when forty minutes remain.

Press T to start the timer. Walk the room in the first fifteen minutes and read briefs: a brief without a denominator now is a wrong number in an hour. Announce the forty-minute mark. Do not debug anyone's SQL for them; ask which check would find the problem.

Before the first defence

Peer rerun · 30 minutes

Clone your colleague's repository. Run capstone/package.py rerun. Ask nothing. Commit the rerun log to their repository.

Press T to start the timer. The peer reports and does not repair. An author whose package is not reproduced may fix it before the defence, and the rerun log stays as it was written: a drift found and repaired is a good story for the defence, not a penalty.

Format

8 minutes for each defence, without the assistant

1 · Choices · 2 minutes

The question. What you delegated, what you kept, and where the data went.

2 · Evidence · 3 minutes

What verification found, which conclusion held in five runs, what your peer's rerun said.

3 · One number, live · 3 minutes

The assessor chooses a headline number. You recompute it in SQL and explain any difference.

Peer feedback. After each defence, everyone writes one strength, one question and one suggestion.

The assistant is closed for the whole defence. Choose the number to recompute from the README before the participant starts speaking, and prefer the one the findings lean on. A recomputation that differs from the README is not a failure by itself: what is scored is whether the participant can explain the difference.

What the packages showed

Strongest patterns

Checks that found something, and disclosures that said what was not verified.

Common gaps

Numbers with no step, denominators left unstated, steps logged from memory.

One surprise

A conclusion that did not hold in five runs, or a null result that did.
